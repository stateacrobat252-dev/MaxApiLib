# Журнал решений (docs/decisions.md)

Здесь фиксируются все решения, которые агент принял сам. Теги:

- `[ASSUMPTION]` — данных не хватало, выбран разумный дефолт.
- `[DEVIATION]` — отклонение от исходного задания (с обоснованием).
- `[BLOCKER]` — задача не решена после трёх попыток.

## Этап 0. Инициализация

### D0.1. Реальный API библиотеки `maxapi` изучен до написания кода

Проверено на колесе `maxapi==1.2.2` (PyPI, репозиторий love-apples/maxapi) и на
документации `dev.max.ru/docs-api`:

- Класс `maxapi.Bot`, метод `get_updates(limit, timeout, marker, types)` возвращает
  «сырой» словарь с ключами `updates` и `marker`.
- Разбор словаря в типизированные события делает
  `maxapi.methods.types.getted_updates.process_update_request(events, bot)`.
- `maxapi.utils.inline_keyboard.InlineKeyboardBuilder` собирает клавиатуру в
  pydantic-объект `AttachmentButton`.
- Вложения в `send_message` принимают **только pydantic-модели**, не словари
  (`SendMessage.fetch()` вызывает `att.model_dump()`), поэтому в `client.py`
  словари конвертируются в модели `maxapi`.

### D0.2. `[ASSUMPTION]` Версии зависимостей

- `maxapi>=1.2,<2` — проверенная версия 1.2.2.
- `requires-python = ">=3.10"` — см. D0.3.

### D0.3. `[DEVIATION]` Python 3.10+ вместо 3.9+

Задание требует «Python 3.9+» и CI-матрицу 3.9–3.12. Однако `maxapi` 1.2.2
объявляет `Requires-Python: >=3.10`, поэтому на 3.9 установка библиотеки
невозможна. Принято: `requires-python = ">=3.10"`, CI-матрица 3.10, 3.11, 3.12,
3.13. Это записано в README и CHANGELOG, чтобы не вводить пользователей в
заблуждение.

### D0.4. `[ASSUMPTION]` Лицензия и авторство

MIT, правообладатель «maxbot-easy contributors» (в задании указана только лицензия MIT).

## Этап 1–2. Исключения и Button

### D1.1. `[ASSUMPTION]` Состав иерархии исключений

Публично экспортируются три класса, как в задании. Базовый `MaxBotEasyError`
наследуется от `Exception`; `MaxBotEasyAPIError` хранит `code` и `original`
(исходная ошибка `maxapi`), `MaxBotEasyNetworkError` — только `original`.

### D2.1. `[ASSUMPTION]` Ограничения значений кнопок

Из документации MAX Bot API: текст кнопки 1–64 символа, `payload` до 256
символов, `url` до 2048 символов, `chat_title` до 128, `chat_description` до 256.
Валидация в `Button` проверяет эти ограничения и подсказывает пример вызова.

### D2.2. `[ASSUMPTION]` Кнопка типа `chat`

`Button.chat(...)` реализована, как требует задание, хотя в `maxapi` класс
`ChatButton` помечен устаревшим (0.9.14) и печатает `DeprecationWarning`. Формат
полей (`type=chat`, `chat_title`, `chat_description`) соответствует документации
MAX Bot API и `maxapi`. Кнопка не используется в примерах.

### D2.3. `[ASSUMPTION]` Поле `intent` не выставляется

MAX API допускает необязательное поле `intent` у callback-кнопки. В `Button.to_dict()`
оно не добавляется: у новичка нет причин менять оформление, а лишнее поле в
запросе не нужно.

## Этап 3–4. TextBox и время

### D3.1. `[ASSUMPTION]` Лимиты клавиатуры проверяются

MAX допускает не более 30 рядов и до 7 кнопок в ряду (до 3 для типов `link`,
`request_contact`, `request_geo_location`). `TextBox.row()` проверяет лимиты и
объясняет ошибку примером — так новичок получает понятное сообщение вместо
ошибки сервера.

### D4.1. `[ASSUMPTION]` Планировщик на потоках

`later()` и `every()` реализованы на `threading.Timer` и фоновом потоке с
`threading.Event`, без глобального «скрытого» цикла событий. Причина: функции
работают и до `bot.run()`, и без бота вообще, а тесты не зависят от таймингов
цикла. Возвращаемые объекты имеют метод `cancel()`.

### D4.2. `[ASSUMPTION]` Форматы `parse_time`

Поддерживаются `10s`, `5m`, `2h`, `1d`, `1w`, а также просто число (`"10"` → 10
секунд и `10` → 10 секунд). Регистр и пробелы игнорируются. Плохой ввод —
`ValueError` с примером.

## Этап 5–7. Bot, client, обработчики

### D5.1. `[ASSUMPTION]` Токен берётся из переменных окружения

`Bot()` без аргумента читает `MAXBOT_TOKEN` (как в задании), затем
`MAX_BOT_TOKEN` (имя, которое использует `maxapi`). Пустой токен — ошибка с
примером вызова.

### D6.1. Клиент `maxapi` создаётся с `auto_requests=False`

Проверено экспериментом: при `auto_requests=True` разбор события вызывает
`get_chat_by_id` (сетевой запрос) и падает на неверном токене ещё до обработки
события. Обёртка создаёт `maxapi.Bot(auto_requests=False)` — события
обрабатываются локально, без скрытых запросов.

### D6.2. `[ASSUMPTION]` Исключения `maxapi` переводится в свои

`InvalidToken`, `MaxApiError` → `MaxBotEasyAPIError`; `MaxConnection`,
`aiohttp.ClientError`, таймаут → `MaxBotEasyNetworkError`. В сообщениях
указывается, что делать пользователю (проверить токен, проверить интернет).

### D7.1. `[ASSUMPTION]` Обработчики выполняются последовательно в одном рабочем потоке

Все обработчики вызываются по очереди в единственном потоке-исполнителе, а не в
потоке цикла событий. Это даёт две вещи: сообщения обрабатываются в том порядке,
в котором пришли, и синхронный `bot.send()` внутри обработчика ждёт результат, а
не подвешивает цикл.

### D7.2. `[ASSUMPTION]` Кнопка нажатия, callback подтверждается автоматически

MAX требует подтверждать нажатие, иначе кнопка «крутится» у пользователя.
Библиотека подтверждает нажатие сама: если обработчик ответил через `bot.reply`,
ответ уходит вместе с подтверждением (сообщение меняется), иначе отправляется
пустое подтверждение. Новичку не нужно об этом знать.

### D7.3. `[ASSUMPTION]` `on_text` без аргумента и `on_message`

`@bot.on_text()` (без фильтра) реагирует на любой текст. `@bot.on_message`
вызывается только если ни один `on_text` не совпал, иначе эхо-бот отвечал бы на
`/start` дважды. Совпадение текста не учитывает регистр, нажатие кнопки «Начать»
в клиенте MAX приходит как `/start`.

### D7.4. `[ASSUMPTION]` Обработчик может принимать 0 или 1 аргумент

Число аргументов определяется по сигнатуре функции. Функция-генератор
(`async def`) тоже поддерживается, но в README не описана: это не для новичков.
